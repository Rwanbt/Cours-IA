Partie 04 du cours

Obsidian — le second cerveau

Application locale gratuite. Aucune donnée n'est envoyée à un service tiers tant qu'aucune synchronisation cloud n'est activée.

Site officiel & téléchargement toutes plateformes : obsidian.md — installeurs Windows .exe, macOS .dmg et Linux AppImage disponibles depuis cette page.

Installation

Windows

winget install Obsidian.Obsidian
# ou installeur .exe : obsidian.md/download

macOS

brew install --cask obsidian
# ou .dmg : obsidian.md/download

Linux

flatpak install flathub md.obsidian.Obsidian
# ou AppImage officielle sur obsidian.md

Créer le vault et le versionner

# Dans Obsidian : "Créer un nouveau vault" → choisir un dossier local, ex.
# Windows : D:\Documents\Obsidian\MonVault
# macOS/Linux : ~/Documents/Obsidian/MonVault

cd MonVault
git init
git add .
git commit -m "chore: initialise le vault"

Plugins communautaires à activer

Réglages → Plugins communautaires → Parcourir, puis installer et activer :

PluginRôle
Local REST APIExpose le vault via l’API locale et fournit désormais aussi un serveur MCP natif. Endpoint recommandé : https://127.0.0.1:27124/mcp/ avec authentification Bearer. Le certificat est auto-signé : il faut l’approuver côté OS/client.
Smart ConnectionsRecherche sémantique entre notes. Utile pour retrouver une décision par le sens ; optionnel pour le fonctionnement du MCP de base.
Obsidian GitCommit/pull/push automatiques du vault. À activer seulement après avoir configuré un remote privé, les exclusions et une stratégie de gestion des conflits.

Dans les réglages du plugin Local REST API, copiez la clé API générée. Ne la placez jamais en clair dans Git : stockez-la dans une variable d’environnement. Le certificat HTTPS local peut être téléchargé depuis le plugin et ajouté aux certificats de confiance du système.

Structure de vault recommandée

MonVault/
├── INDEX.md              # hub de navigation central
├── LOG.md                # journal chronologique, append-only
├── SCHEMA.md             # conventions frontmatter + wikilinks
├── ProjetA/
│   ├── _memory/memory.md
│   └── decisions-log.md
└── _global/

Graphify — le graphe de dépendances

À vérifier avant de figer un script

Graphify évolue rapidement et sa méthode de distribution peut changer. Avant une installation en masse (ex. poste de plusieurs étudiants), vérifier la commande d'installation exacte sur le dépôt officiel du projet plutôt que de copier une commande figée dans ce document.

Utilisation une fois installé (identique sur les 3 OS)

# Se placer à la racine du projet à indexer
cd mon-projet

# Première indexation — construit graphify-out/graph.json + GRAPH_REPORT.md
graphify .

# Lire le rapport avant toute question d'architecture
cat graphify-out/GRAPH_REPORT.md

# Interroger le graphe au lieu de grepper
graphify query "processRequest"
graphify path "ModuleA" "ServiceB"

# Ré-indexer après des modifications (rapide — AST seulement)
graphify update .

Partie 06 du cours

Configurer l'agent « auto »

Danger — à lire avant d'activer

`permission: {"": "allow"}` supprime les demandes de confirmation pour cet agent personnalisé. On le conserve volontairement dans ce cours : il montre comment créer un agent primaire réutilisable depuis le CLI et le Desktop. Réservez-le à un dépôt Git propre, une branche dédiée et un environnement sans identifiants de production. Git protège les fichiers suivis, mais ne restaure pas les effets externes (base distante, suppression hors dépôt, publication, etc.).

1. Localiser / créer le fichier de config globale

Windows PowerShell

New-Item -ItemType Directory -Force `
  "$HOME\.config\opencode"
# fichier : C:\Users\<UTILISATEUR>\.config\opencode\opencode.jsonc

macOS Terminal

mkdir -p ~/.config/opencode
# fichier : ~/.config/opencode/opencode.jsonc

Linux Terminal

mkdir -p ~/.config/opencode
# fichier : ~/.config/opencode/opencode.jsonc

2. Ajouter l'agent (ne pas remplacer un bloc "agent" existant)

Si la clé "agent" existe déjà dans le fichier, n'ajouter que la sous-clé "auto" à l'intérieur — sans supprimer les autres agents déjà déclarés.

{
  "agent": {
    "auto": {
      "description": "DANGEROUS — runs all tools without permission prompts.",
      "mode": "primary",
      "color": "error",
      "app_hidden": false,
      "cli_hidden": false,
      "permission": { "": "allow" }
    }
  }
}

3. Vérifier que la configuration est chargée

Windows PowerShell

opencode debug config | Select-String '"auto"'

macOS / Linux Terminal

opencode debug config | grep '"auto"'

Puis

# Redémarrer OpenCode Desktop.
# L'agent "auto" apparaît dans le sélecteur d'agents.
Pourquoi garder cette méthode

OpenCode propose aussi des mécanismes natifs d’auto-approbation, mais cet agent personnalisé reste pertinent pédagogiquement : il montre la structure d’un agent primaire, son exposition dans les deux interfaces et la façon de versionner une politique de permissions.

Partie 06 du cours

Brancher le MCP Obsidian

Local REST API inclut désormais directement un serveur MCP. On évite donc un package MCP tiers et on connecte OpenCode à l’endpoint HTTPS local du plugin. Ajoutez le bloc `mcp` dans le même `opencode.jsonc`, à côté du bloc `agent`, sans écraser les autres serveurs.

{
  "mcp": {
    "obsidian": {
      "type": "remote",
      "url": "https://127.0.0.1:27124/mcp/",
      "enabled": true,
      "oauth": false,
      "headers": {
        "Authorization": "Bearer {env:OBSIDIAN_API_KEY}"
      }
    }
  }
}
ÉlémentValeur / action
Endpoint MCPhttps://127.0.0.1:27124/mcp/
AuthentificationAuthorization: Bearer $OBSIDIAN_API_KEY
CertificatAuto-signé : télécharger/faire confiance au certificat Local REST API dans l’OS ou le client.
Fallback atelierHTTP 127.0.0.1:27123 uniquement si nécessaire et explicitement activé dans le plugin.

Redémarrez OpenCode puis vérifiez le serveur avec `opencode mcp list`. Demandez ensuite à l’agent de lire une note non sensible contenant une valeur unique que le modèle ne peut pas deviner. Si HTTPS échoue, diagnostiquez d’abord la confiance du certificat avant de basculer vers l’endpoint HTTP local.

HTTPS est le chemin recommandé

Le serveur MCP officiel de Local REST API écoute sur https://127.0.0.1:27124/mcp/. Le certificat est auto-signé : il est normal qu’un client le refuse tant qu’il n’a pas été approuvé. Le plugin permet de récupérer le certificat local ; ne désactivez la vérification TLS qu’en dernier recours sur localhost.

Si le script ne convient pas à votre environnement, gardez le dépôt cloné comme source canonique. Prompts prêts à copier-coller dans OpenCode

Prompt 1 — diagnostic puis configuration « auto » (chaînage automatique)

Tu es mon agent de bootstrap local dans OpenCode.
Objectif : préparer ce poste pour OpenCode CLI + Desktop, Obsidian et ai-native-dev-stack, puis configurer l’agent personnalisé « auto » partagé par le CLI et le Desktop — diagnostic puis configuration enchaînés sans validation intermédiaire.

=== PHASE 1 — DIAGNOSTIC (lecture seule) ===

Détecte l'OS, le shell, le dossier courant et les versions de git, opencode, node et python. Localise la configuration OpenCode globale et le vault Obsidian. Vérifie Local REST API sans afficher sa clé, Ollama et l'existence d'ai-native-dev-stack.

Affiche le diagnostic en trois colonnes : déjà installé, absent, à vérifier manuellement. Ne fais que lire — n'écris rien à ce stade.

=== PHASE 2 — CONFIGURATION « AUTO » (enchaînement automatique) ===

Enchaîne immédiatement, sans attendre de validation :
1. Travaille uniquement dans la configuration globale identifiée.
2. Si un bloc agent existe, fusionne seulement la sous-clé nécessaire : ne remplace jamais les autres agents.
3. Vérifie la syntaxe JSONC, lance la commande de debug de configuration et confirme que « auto » est chargé.
4. Affiche le chemin exact, le diff prévu, les risques et la commande de rollback.
5. Ne committe et ne pousse rien.

Rappel : conserve volontairement l’agent personnalisé « auto » ; ne le remplace pas par `--auto`. Il sert ici à démontrer la création d’un agent primaire réutilisable. Réserve-le à une branche dédiée et à un environnement sans secrets de production.

=== SORTIE ATTENDUE ===

Diagnostic (Phase 1) puis résumé concis des modifications effectuées (Phase 2), avec chemin exact du fichier et commande de debug ayant confirmé le chargement de l'agent « auto ».

Prompt 2 — brancher Obsidian et structurer le vault

Configure le MCP natif HTTPS de Local REST API pour OpenCode et prépare l’architecture documentaire du vault.

Vérifie Local REST API sans afficher la clé. Utilise en priorité `https://127.0.0.1:27124/mcp/` avec `Authorization: Bearer {env:OBSIDIAN_API_KEY}`. Vérifie ou installe la confiance du certificat auto-signé ; n’utilise l’HTTP 127.0.0.1:27123 qu’en repli local explicite. Ajoute ou fusionne le bloc MCP sans écraser les autres serveurs. Teste la connexion en lisant une note non sensible contenant une valeur unique.

Inspecte les dossiers existants avant toute création. Propose ensuite une architecture minimale : INDEX, LOG, _memory, projets, décisions et handoffs. Crée uniquement les éléments validés, avec frontmatter et wikilinks conformes aux conventions du vault. Termine par une vérification de lecture via MCP.

Prompt 3 — installer Graphify et cartographier le projet

Installe et initialise graphify sur le projet courant.

Vérifie le dépôt, la branche Git et l'état dirty. Si graphify est absent, propose la commande adaptée à l'OS sans l'exécuter avant validation. Génère le graphe en excluant node_modules, target, build, dist, vendor et les secrets.

Lis GRAPH_REPORT.md et graph.json. Résume les modules centraux, dépendances entrantes, cycles éventuels, zones à risque et fichiers non analysés. Cherche les consommateurs et call sites : un helper testé ne prouve pas que la fonctionnalité est branchée. Après modification, utilise graphify update.

Prompt 4 — installer ai-native-dev-stack, skills et hooks

Installe "https://github.com/Rwanbt/ai-native-dev-stack" sur ce projet et rends ses règles opérationnelles.

Vérifie si le dépôt est déjà cloné. Lis son README, AGENTS.md, scripts d'installation, skills et hooks avant exécution. Présente les fichiers qui seront créés ou modifiés. Utilise `scripts/setup-agents.ps1` sous Windows PowerShell et `scripts/setup-agents.sh` sous Linux/macOS. Commence si possible par le mode dry-run, puis vérifie avec le mode check. Pour OpenCode, implémente une compatibilité à deux chemins : `instructions` quand la version utilisée le résout réellement, et maintien du `~/.config/opencode/AGENTS.md` global géré comme fallback pour OpenCode V2 tant que `instructions` n’est pas injecté au modèle. Lance verify-ai-docs. Ne modifie pas les fichiers métier, ne committe et ne pousse rien. Termine par un rapport des skills, hooks, vérifications et limites restantes.

Prompt 5 — créer un dépôt GitHub privé pour le vault et le synchroniser

Tu es mon agent de configuration Git dans OpenCode.
Objectif : créer un dépôt GitHub privé pour le vault Obsidian actuel, y lier le vault local et activer la synchronisation automatique, en sécurité.

=== PHASE 1 — DIAGNOSTIC ===

Détecte l'OS et le shell. Localise le vault Obsidian actif et confirme qu'il contient déjà un dépôt Git initialisé. Vérifie la présence du binaire gh (GitHub CLI) et l'authentification GitHub actuelle, sans afficher aucun token.

Affiche : emplacement du vault, statut Git (clean ou modified), branche courante, remote configuré, authentification GitHub disponible ou manquante.

=== PHASE 2 — CRÉATION DU DÉPÔT PRIVÉ ===

Si aucun remote n'est configuré :
1. Propose le nom du dépôt (par défaut le nom du dossier du vault) en PRIVATE.
2. Préfère GitHub CLI : `gh auth status`, puis `gh auth login` si nécessaire, puis `gh repo create NOM --private --source=. --remote=origin --push`.
3. Ne place jamais un Personal Access Token dans l'URL d'un remote, une commande copiée dans l'historique ou un fichier de configuration. Si `gh` n'est pas disponible, utilise Git Credential Manager / le mécanisme d'authentification Git standard de l'OS.
4. Le remote doit rester propre, par exemple `https://github.com/USER/NOM.git`.
5. N'accorde que les droits nécessaires et ne journalise aucun secret.
6. Affiche le diff de remote et la commande de rollback `git remote remove origin`.

=== PHASE 3 — SYNCHRONISATION OBSIDIAN GIT ===

Vérifie que le plugin communautaire Obsidian Git est installé et actif. Configure :
- Vault backup interval : 30 (minutes)
- Auto-push on interval : activé
- Commit message template : vault: auto-sync {{date}} {{time}}
- Exclusions : .obsidian/workspace.json, .trash/, fichiers de plus de 10 Mo

Vérifie qu'un premier commit/push manuel fonctionne et que la page GitHub du dépôt affiche bien les notes.

=== SORTIE ATTENDUE ===

Diagnostic Phase 1, dépôt privé créé et lié (Phase 2), plugin Obsidian Git configuré et validé par un push manuel concluant (Phase 3). Aucune clé API ni token affiché.
Sorties attendues

AGENTS.md référencé, skills actifs, hook vérifié, graphe Graphify lisible, architecture de vault claire, dépôt GitHub privé lié au vault et premier push manuel concluant.
